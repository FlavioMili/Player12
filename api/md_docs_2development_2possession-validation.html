Ownership and compatibility audit

There are 92 classified ball fields: 48 in the sole private possession record (43 original facts plus five policy fields) and 44 physical/planning/eligibility/ diagnostic fields outside it. Nine history fields are nested in the owner record. Only the selected Aardvark/Binturong owner files mutate backing. Four whole-ball resets occur there; each saves/restores history. Consumers borrow const views or hold independent value snapshots. Reviewed alias hits are const MatchBall references, render-value projections or camera focus values, not writable aliases to possession backing. The scanner is lexical; C++ private/const access supplies the language-level boundary.

No temporary writable mirror remains to remove. Retain these intentional compatibility paths:

  • Per-match Aardvark policy and dispatchers, required for frozen comparisons.
  • Broad attachment queries and LEGACY_ATTACHED, which preserve existing body/rule/controller meanings without asserting confirmed foot control.
  • MatchRenderBall, an independent renderer value projection.
  • Recording format 1 fallback, format 2 selection and explicit replay overrides.
  • check_possession_writers.cjs, a forwarding command name for the boundary audit, not a state adapter.

The inspector displays (control), (claim), (attached) or (restart) for attachment, plus (expected) independently. Its follow-ball tooltip describes broad attachment. Trace/controller/claim queries are the source for debugging; delivery expectation, last contact and chasing intent are not evidence of control.
